→ **鸿蒙 6.0.2（API 22）产物**。你说的鸿蒙 7 是 API 23+，**必须实测兼容性**，不可假设。

### 2.2 预编译静态库（`fanxing_rime_har/src/main/cpp/lib/`）

| 库 | 大小 | 用途 |

| **librime.a** | **18.1 MB** | Rime 引擎本体 |

| libleveldb.a | 0.70 MB | 用户词典/调频存储 |

**这是本方案的核心价值**：原评估里「5–8 周」的大头——交叉编译 librime + boost + lua + opencc + leveldb + marisa + glog 到 OHOS——**已经有人做完了**。

头文件齐全：`include/rime/`（含 `rime_api.h`、`rime_levers_api.h`）、`include/opencc/`、`include/marisa/`、`include/yaml-cpp/`、`include/leveldb/`。

### 2.3 NAPI 接口（`fanxing_napi.cpp`，278 行，模块名 `fanxing_rime`）

| 接口 | 签名 | 说明 |
|---|---|---|
| `initEngine` | `(sharedPath: string) => void` | 建 `<path>_user` 目录后 `setup` + `initialize` + `start_maintenance(true)` |
| `checkStatus` | `() => number` | 1=部署中，0=就绪，-1=异常 |
| `switchSchema` | `(schemaId: string) => number` | 懒创建 session，`select_schema` |
| `getCandidates` | `(input: string) => {candidates: string[], preedit: string, pinyinChoices: string[]}` | **每次 clear_composition 后逐字符重喂整串**，翻页收集最多 50 个 |
| `selectCandidate` | `(index: number) => number` | 翻页定位后 `select_candidate_on_current_page` + `commit_composition`，**不返回上屏文本** |

## 三、能白拿什么 vs 要自己做什么

### ✅ 白拿（省掉数周）

1. **librime 引擎二进制**（arm64-v8a），含 Lua 支持 → **电脑版的 12 级 lua 滤镜、三向反查、自造词、自调频逻辑可原样复用**
2. **OpenCC 集成**（libopencc.a）→ 简繁切换直接用
3. **rime_api.h** → 可以自己扩展 NAPI，不必依赖作者那 5 个接口
4. MIT 许可，商用无阻

### ⚠️ 必须自己做

| # | 事项 | 说明 | 量级 |
|---|---|---|---|
| 1 | **重写 NAPI 桥** | 作者的 5 个接口是 Demo 级：无删除键、无翻页、无光标；`getCandidates` 每次重喂整串（性能差且丢编辑状态）；`selectCandidate` 不返回上屏文本；**把候选 `comment` 当成「拼音候选」返回**——三生输入法的三向反查注释会直接错位 | 中 |
| 2 | **键盘 UI** | 仓库里的 `MainPage.ets` 是 `Hello World` 模板，**没有输入法界面** | 大 |
| 3 | **IME Kit 接入** | 没有 `InputMethodExtensionAbility`、没有 `InputClient` 上屏、没有面板管理 | 大 |
| 4 | **电脑版配置/词库移植** | schema（`wubi_pinyin`）、12 级滤镜、`rime.lua` 接线、7 组词库、OpenCC 数据，搬进鸿蒙沙盒 | 中 |
| 5 | **自造词/自调频落盘** | Rime `userdb`/`user.txt` 在鸿蒙沙盒的路径与持久化策略 | 小—中 |
| 6 | **签名与打包** | 作者 `build-profile.json5` 里**明文写着他自己的签名密钥与密码**（`C:\Users\cocochuvio\...`）。**必须全部删掉换自己的**，绝不能沾 | 小 |

## 四、目标架构

```
┌─────────────────────────────────────────────┐
│  InputMethodExtensionAbility (自己的)        │
│    ├─ KeyboardController  面板/键盘显隐       │
│    └─ InputClient         insertText 上屏     │
├─────────────────────────────────────────────┤
│  ArkUI 键盘壳 (自己的, 手机/平板)             │
│    ├─ 候选栏（候选 + 三向反查注解 comment）    │
│    ├─ 字母键盘 / 符号键盘 / 数字键盘           │
│    └─ 状态键（中英、简繁、设置）               │
├─────────────────────────────────────────────┤
│  NAPI 桥 (自己重写, 替换 fanxing_napi.cpp)    │
│    暴露 process_key / get_context /          │
│    commit / delete / 翻页 等完整能力          │
├─────────────────────────────────────────────┤
│  libfanxing_rime.so  ← CMake 链接            │
│    librime.a + liblua.a + libopencc.a + ...  │
├─────────────────────────────────────────────┤
│  电脑版资产（原样搬）                          │
│    wubi_pinyin.schema.yaml                   │
│    12 级 lua 滤镜 + rime.lua                  │
│    wubi86 / cn_pinyin / zh2en / en2zh 词库    │
│    OpenCC s2t.json + STCharacters/STPhrases   │
└─────────────────────────────────────────────┘
```

**核心判断**：因为有 librime.a + Lua，电脑版的八项功能（五笔、拼音、中英、混输、简繁、三向反查、自造词、自调频）**全部走原配置生效**，不需要用 ArkTS 重写反查算法。我前面搭的「ArkTS 从零重写引擎」纯属重复造轮子，应废弃。

## 五、集成步骤（分阶段）

### 阶段 0 · 前置闸门（先做，不通就别投）

1. 用 DevEco Studio 编译 `fanxing_rime_har` → 产出 `fanxing_rime_har.har`
2. 建一个最小 IME 壳，**验证未上架调试签名的输入法能否进入系统输入法列表**
3. **在鸿蒙 7（API 23+）真机上验证**该 API 22 产物能否加载（`libfanxing_rime.so` 是否被拒）
4. 验证 arm64-v8a 在目标机型可用（模拟器 x86_64 不行）

### 阶段 1 · 引擎点火

5. HAR 放进 `libs/`，`oh-package.json5` 声明 `file:./libs/fanxing_rime_har.har`
6. 把 `initEngine` 的 `sharedPath` 指向应用沙盒，把电脑版 `rime/` 配置与词库铺进去
7. 用 `checkStatus` 等部署完成，`switchSchema('wubi_pinyin')` 切方案

### 阶段 2 · 键盘与上屏

8. 写 `InputMethodExtensionAbility` + `InputClient` 上屏 + 面板管理
9. 写 ArkUI 键盘（手机/平板布局）+ 候选栏
10. 打通：按键 → 输入串 → `getCandidates` → 候选栏 → 选词 → `insertText` 上屏

### 阶段 3 · 补齐三生能力

11. **重写 NAPI 桥**，暴露逐键 `process_key`、`get_context`（含 `comment` 用于反查注解展示）、删除/翻页/选词
12. 候选栏展示三向反查注解（打五笔显拼音、打拼音显五笔码、打英文显两者）
13. 简繁开关、中英切换、状态指示

### 阶段 4 · 数据与打磨

14. 自造词/自调频在沙盒的读写与「重置调频」
15. 图标、候选排序、性能（首启部署耗时）
16. 打包 `.hap`、真机全量自测

## 七、与「纯 ArkTS 重写」路线对比

| 维度 | HAR 路线（本方案） | 纯 ArkTS 重写 |
|---|---|---|
| 引擎 | 复用 librime.a（已完成） | 从零写五笔/拼音/切分/反查引擎 |
| 电脑版资产 | **原样复用**，八项功能白拿 | 全部重写，且难保证一致 |
| 三向反查 | 原 lua 滤镜，行为一致 | 需重写 436 行算法 + 重建索引 |
| 自造词/自调频 | librime 原生 userdb | 需自建方案 |
| 主要工作量 | NAPI 桥 + 键盘 UI + IME 接入 | 引擎 + 键盘 UI + IME 接入（更多） |
| 风险 | 引擎依赖第三方 / API 版本 | 算法对齐度 / 性能 |

**结论：HAR 路线明显更优**，前提是阶段 0 的两道闸门能过。

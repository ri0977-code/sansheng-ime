## 1. 值守的提案与实测结果

提案原话（值守日志）：

> ⇒ **交付验收顺序改为：源码 grep keyboardShow ≥1 → 打包产物 abc 里 keyboardShow ≥1 → 才允许装机**；
> 产物里 0 就不装，直接退回去改（省一次装机 + 一次主人输密码）。

实测（只读）：

| 位置 | `keyboardShow` | `hideKeyboard` | `showPanel` | `chevron_down` | `BottomBar` |
|---|---|---|---|---|---|
| `entry/src/**`（源码） | 0 | 有（控制器定义 + 页面调用） | 有 | 有（写成 `$r('sys.symbol.chevron_down')`） | 有 |
| `entry/build/default/intermediates/loader_out/default/ets/modules.abc`（01:17:18，451,308 B） | **0** | 3 | 2 | **0** | 2 |

三条理由，任一条都够否掉：

1. **符号不存在**：我们的代码里没有 `keyboardShow` 这个名字，收起键盘走的是 `panel.hide()`
   （控制器 `:291-300`），弹出走 `showPanel()`→`panel.show()`（`:232-241`）。拿一个不存在的
   符号当必要条件 ⇒ 无论 CodeArts 改得多对，闸门永远 FAIL ⇒ 等于永久阻断构建。
   这正是 H-115 那类「把提示级/不可能满足的判据算进阻断」的坑，只是这次更糟：判据本身是假的。
2. **字符串判据在这个栈上天生不可靠**：abc 里 `chevron_down` 也是 0 次，因为
   `$r('sys.symbol.xxx')` 编译成数字资源 id，不保留字面量。也就是说「产物里搜不到」和
   「功能不存在」本来就是两件事，用它做闸门会产生反方向的误判。
3. **它想解决的问题已经被更前面的闸门解决了**：结构判据（源码层、每个并列 Row 都要有
   `hideKeyboard`）在构建之前就能判，成本零；产物层再 grep 一遍只是把同一个事实换成一个
   会漂移的表示形式。构建与交付之间的真正一致性判据是 **字节数逐字节比对**（我构建的
   unsigned HAP 大小 = 他报的数），不是符号搜索。

值守的动机（省一次装机、省一次主人输密码）是对的，我照它采纳的部分已经落地：装机必须带
`-Target 7GL0226408083897`（W-146 的「不许猜机器」），结构闸门成为构建第 0 步。

## 3. precheck 的假阳性与修法（这次的真错误）

现象：01:23 我跑 `scripts/h106_precheck.py`，明明没交付，却打印
`[OK] 记账行含 unsigned 字节数 —— 最新: ...`。

根因两层，第一层修完又露出第二层：

- 第一层：判据是「WIP/MAILBOX **最新一行**里有字节数」，而最新一行是我自己写的 M-108，
  里面那句「形如 `1234567B`」是我的示例 ⇒ 判据被自己的说明文字骗过。
- 第二层：改成「只扫 CodeArts 署名 + 提到 H-106/底栏/收起键 的行」后，命中
  `M-030-review-re` 这类**历史**交付行，一次吐出 80 个旧字节数（`28175230 / 24362774 / ...`）。
  台账只会越长，任何关键字筛法迟早被历史行撑爆。

最终修法（**位置语义**）：待验收交付 = 台账尾部那一行是 CodeArts 署名，且里面有 ≥6 位、
且不等于示例 `1234567` 的字节数。副作用正好是我要的：我写完验收行之后，尾部又变成我的行 ⇒
判「无待验收交付」⇒ 值守不会重复构建、重复安装同一个 HAP。

判据自身现在带自测（`--selfcheck`），6 个样本，其中一条就是这次误报的原样复现：

```
== 交付判据自测（坏样本必须判 FAIL，好样本必须判 OK）==
  OK  期望=FAIL 实际=FAIL 尾部交付=- 数=[]  台账尾部还是我的指令（他没交付）
  OK  期望=FAIL 实际=FAIL 尾部交付=M-108-re 数=[]  尾部是 CodeArts 但没报字节数
  OK  期望=FAIL 实际=FAIL 尾部交付=M-108-re 数=[]  尾部是 CodeArts 但只抄了示例 1234567B
  OK  期望=FAIL 实际=FAIL 尾部交付=- 数=[]  他交付后我又写了验收行（不重复构建同一个 HAP）
  OK  期望=FAIL 实际=FAIL 尾部交付=- 数=[]  上一版误报的原样复现：尾部 M-108 是我写的
  OK  期望=OK   实际=OK   尾部交付=M-108-re 数=['28179829']  尾部是 CodeArts 且报了真实字节数
结论：判据可信        # exit=0
```

结构判据的三向自测仍然成立（改动没碰结构部分）：

- HEAD 副本 `--kb` ⇒ exit 0（「BLOCK 全过」）；
- 半对样本（只在字母分支加键）⇒ 阻断 1 项，只报 symbol；
- 当前工作树 ⇒ 阻断 5 项：`底栏[symbol]有收起键`、`底栏[else]有收起键`、`已做 checkpoint 提交`、
  `台账尾部是 CodeArts 的交付行`、`交付行含 unsigned 字节数`（exit 2）。

## 4. 这一轮的教训（写给自己的）

一条判据要同时跑**已知好样本**和**已知坏样本**，而且坏样本里必须包含「我自己写的那段说明文字」
——否则判据会被作者的措辞喂出假 OK。这条已经写进 `--selfcheck`，不再是口头纪律。

提交：`e030f4e fix(h106-precheck): 交付判据不再被自己的示例文字和历史行骗过`。

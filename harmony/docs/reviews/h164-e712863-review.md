## 二、逐问题回答

### 问题 a：ArkUI List 的 `onScrollIndex` 在初始布局与数据整体替换时会不会回调？`candDragArmed` 够不够？

**结论：会回调；`candDragArmed` 在 `e712863` 单独不够，但 `0b199eb` 加固后够了。**

ArkUI List 的 `onScrollIndex(first, last)` 在以下场景会回调：
1. **初始布局完成** — List 首次渲染后报告可见区域 `first=0, last=N`
2. **数据整体替换** — `scrollCandidates()` 返回新数组（`uiPageStart` 变化或引擎换页后 `allCandidates` 替换），List 重新布局后回调
3. **用户滚动** — 手指拖动或惯性滚动期间持续回调
4. **`scrollToIndex()` 程序调用** — `candScrollToStart()` 触发 List 滚回 index 0，回调 `first=0`

**`e712863` 的 `candDragArmed` 单独不够的场景**：

场景 1（初始布局）：`candDragArmed=false` → 不续页 ✓
场景 3（用户滚动）：`candDragArmed=true`（Down 置位）→ 可续页 ✓
场景 4（程序 `scrollToIndex`）：`candDragArmed` 状态取决于此时手指是否按下 — 如果 `setUiListener` 在用户拖动期间回调（preeditChanged），`candDragArmed` 仍为 `true`，`scrollToIndex(0)` 触发 `onScrollIndex(0, N)`，此时 `last < items.length - 1`（刚滚回头部），不会续页 ✓

**但场景 2 有风险**：如果用户正在拖动（`candDragArmed=true`），引擎异步回调 `setUiListener`（baseChanged），`allCandidates` 被替换为新页数据。此时 `scrollCandidates()` 返回新数组，List 重新布局，`onScrollIndex` 回调。如果新页数据恰好 `last == items.length - 1`（新页只有少量候选），且 `candDragArmed` 仍为 `true`，就会误触发续页。

**`0b199eb` 的加固解决了这个问题**：在 `setUiListener` 的 `preeditChanged` 和 `baseChanged` 分支都加了 `candDragArmed = false` + `candDragMoved = false` + `candLastVisible = 0`（lines 945-948, 955-957）。这意味着引擎回调时续页许可被强制撤销，后续 `onScrollIndex` 回调不会误续页。

**残留边界**：如果 `setUiListener` 回调与 `onScrollIndex` 回调之间存在时间窗口（ArkUI 事件循环的微任务/宏任务顺序），理论上 `onScrollIndex` 可能先于 `setUiListener` 的清理执行。但 `candTryContinue()` 内部在调用 `flipPage(1)` 前先检查 `this.baseIndex === prevBase && this.allCandidates.length === prevLen`（line 793），如果引擎已经换了页（baseIndex 变了），这个检查会失败，`pendingForwardAbs` 被撤销。所以即使误触发续页，引擎侧也不会翻第二页。**无用户可见后果**。

### 问题 b：`ForEach` key 用 `uiPageStart + index` 在跨页续取时是否会复用错节点？

**结论：不会复用错节点。key 设计正确。**

当前代码（line 1212）：
```typescript
ForEach(this.scrollCandidates(), (cand: RimeCandidate, index: number) => {
  // ...
}, (cand: RimeCandidate, index: number) => `cand_${this.uiPageStart + index}_${cand.text}`)
```

key 格式 = `cand_${uiPageStart + index}_${cand.text}`，其中 `index` 是 ForEach 内部序号（0-based），`uiPageStart` 是当前切片起点。

**续页场景**（`uiPageStart` 从 0 变为 20）：
- 旧数组：`allCandidates.slice(0)` = [item0..item49]，key: `cand_0_xxx` .. `cand_49_xxx`
- 新数组：`allCandidates.slice(20)` = [item20..item49]，key: `cand_20_xxx` .. `cand_49_xxx`
- 交集：`cand_20_xxx` .. `cand_49_xxx` — 这些 key 在新旧数组中都存在
- ForEach 行为：复用 key 匹配的节点（20-29 个新节点创建，0-19 个旧节点删除，20-49 对应节点复用）

这是**正确**的。因为新数组的第 0 项 = 旧数组的第 20 项（同一个 `RimeCandidate` 对象引用），key `cand_20_text` 在两边一致，ForEach 正确复用而非重建。

**引擎翻页场景**（`baseIndex` 变化，`allCandidates` 完全替换）：
- 旧数组 key: `cand_0_oldText` .. `cand_49_oldText`
- 新数组 key: `cand_0_newText` .. `cand_49_newText`（`uiPageStart` 重置为 0 或 `pendingForwardAbs - baseIndex`）
- 无交集 → 全部重建。正确（内容完全不同）

**同页重码场景**（同一 Rime 菜单页内两个候选 text 相同）：
- key 包含 `uiPageStart + index`（唯一序号），即使 text 相同，key 也不会重复
- 不会复用错节点 ✓

### 问题 c：`.gesture` 替代 `priorityGesture` 后，H-034 与 H-059 是否有功能回退？

**结论：无功能回退。**

**H-034（候选栏滑动翻页）**：
- 旧设计：`priorityGesture(SwipeGesture(Horizontal))` 在候选栏整个区域拦截左右滑 → 一滑一页 + 500ms 防抖
- 新设计：`.gesture(SwipeGesture(Horizontal))` 降为普通优先级
  - List 区域内的左右滑 → 交给 List 原生连续滚动（H-164 预期行为）
  - 非 List 区域（左右内边距、展开键 36vp）的左右滑 → 仍触发 SwipeGesture → 一滑一页 + 500ms 防抖

**回退分析**：
- List 区域内：从"一滑一页"变为"连续滚动" — 这是 H-164 的**预期变更**，不是回退
- 非 List 区域：SwipeGesture 仍生效 → 一滑一页功能保持 ✓
- **跨区域滑动**：手指从 List 区域开始滑动，List 捕获触摸序列（因为 `.gesture` 优先级低于子组件原生手势），SwipeGesture 不会触发。这是预期行为（用户在 List 上滑就是要连续滚动）。反方向（从非 List 区域开始滑入 List）同理，SwipeGesture 在非 List 区域捕获手势。**无回退**。

**H-059（展开态翻页）**：
- 展开态时 `ExpandedPanel()` 覆盖键盘区，但 `CandidateBar()` 仍在顶部可见
- `.gesture` 仍挂在 `CandidateBar` 上 → SwipeGesture 仍能触发翻页
- 展开态没有 List 在 CandidateBar 内竞争手势（ExpandedPanel 是独立组件）→ SwipeGesture 正常生效
- **无回退** ✓

**潜在关注点**（非回退，但值得真机验证）：
- `.gesture` 的 SwipeGesture 与 List 原生滚动的边界判定由 ArkUI 框架处理。如果 SwipeGesture 的 `speed: 20` 参数与 List 滚动的判定阈值不协调，可能出现"快速滑被 List 吃掉、慢速滑触发 SwipeGesture"的不一致体验。这需要真机验证（判据①）。

### 问题 d：`List` + `layoutWeight(1)` + `ListItem.width(number)` 在横屏 2832×1280 下有无测量异常？

**结论：预期无测量异常，但需真机验证。**

代码配置（lines 1214-1217）：
```typescript
.listDirection(Axis.Horizontal)
.lanes(1)
.layoutWeight(1)
.height(this.candRowHeight())
```

ListItem 宽度（line 1207）：
```typescript
.width(this.candItemWidth(cand.text))
```

`candItemWidth(text)` = `Math.max(28, Math.ceil(estimateCandWidth(text, candFontSize())) + 14)` — 返回 vp 数值

**横屏分析**：
- 2832×1280 px @ 3x density ≈ 944×427 vp
- `layoutWeight(1)` 让 List 在 Row 中占据展开键（36vp）左侧的剩余宽度 ≈ 908vp
- `ListItem.width(number)` 单位是 vp，`candItemWidth` 估宽基于 `candFontSize()` 和文字长度，与屏幕宽度无关
- 横屏 `candRowHeight()` 压缩 6vp（`barHeight<40` 时），不影响宽度测量

**潜在异常**：
1. **`layoutWeight(1)` 在横向 List 中的语义**：`layoutWeight` 在 ArkUI 中用于 Flex/Row 内分配剩余空间。List 用 `layoutWeight(1)` 会占据父 Row 的剩余宽度，这在横屏下应该正常（剩余宽度更大）。
2. **ListItem 宽度之和超过 List 可视宽度**：这是预期行为 — List 横向滚动就是为了让内容超出可视宽度。`scrollBar(BarState.Off)` + `edgeEffect(EdgeEffect.None)` 确保滚动时不显示滚动条和边缘效果。
3. **`candItemWidth` 在横屏下的精度**：横屏 `candFontSize()` 可能与竖屏不同（如果字号随布局变化），但当前代码中 `candFontSize()` 返回固定值（不随横竖屏变化），所以估宽精度一致。

**需真机验证**：判据⑨（横屏复跑）会覆盖此问题。`ltap-measure.py` 可量候选行 y 坐标和续页像素证据。

### `.onDisAppear` 后控制器是否真的失效？

ArkUI `.onDisAppear` 在组件从组件树移除时触发。对于 `CandidateBar` 中的 List：
- `CandidateBar()` 是 Builder 函数，在 `KeyboardIndex` 的 `build()` 中被调用
- `CandidateBar` 始终在 `build()` 中渲染（不是条件渲染），所以 List 不会因布局切换而 `onDisAppear`
- List 只在整个 KeyboardIndex 页面被销毁时（如导航到 AboutPage）才会 `onDisAppear`

**`onDisAppear` 后 `candListReady=false` 的影响**：
- `candScrollToStart()` 直接 return → List 不会滚回片首
- 但此时 List 已经不在组件树中，用户看不到它 → **无用户可见后果**
- 当用户回到键盘页面，List 重新 `onAppear` → `candListReady=true` → 守卫恢复正常

**Qoder 在 M-180 中提到的取舍**："若只会脱离可视区而不注销，`candListReady=false` 会让换片不滚回片首" — 这个取舍是合理的。在当前代码结构下，List 不会"脱离可视区而不注销"（它要么在组件树中，要么不在），所以这个取舍实际上不会被触发。

## 四、`0b199eb` 甩动续页加固复核

### `candDragMoved` + `onScrollStop` 的设计

问题：ArkUI List 的甩动（fling）惯性可能在手指抬手后才滚到尾部，此时 `onScrollIndex` 回调时 `candDragArmed` 已被 `TouchType.Up` 清除 → 续页不触发。

解法：
1. `TouchType.Move` 时置 `candDragMoved=true`（line 1233）
2. `TouchType.Up` 时如果 `candDragMoved=true`，不清 `candDragArmed`（line 1237-1238）— 保留许可等 `onScrollStop`
3. `onScrollStop` 兜底调 `candTryContinue(candLastVisible)`（line 1254），然后清 `candDragArmed` + `candDragMoved`（lines 1255-1256）

**白点/轻点保护**：`TouchType.Up` 时如果 `!candDragMoved`（手指按下后没移动就抬起），立即清 `candDragArmed`（line 1238）— 防止"点一下候选栏就续页"。

**内容/换页清许可**（lines 945-948, 955-957）：`setUiListener` 的 `preeditChanged` 和 `baseChanged` 分支都清 `candDragArmed` + `candDragMoved` + `candLastVisible` — 防止数据刷新触发的 `onScrollIndex`/`onScrollStop` 误续页。

**评估**：设计正确，覆盖了甩动续页的核心场景。残留风险：
- `onScrollStop` 在 ArkUI 中的触发时机是否可靠（是否每次惯性滚动结束后都会回调）— 需真机验证
- 如果 `onScrollStop` 不回调（框架 bug 或边界情况），`candDragArmed` 会一直保持 `true` 直到下一次触摸 — 但下一次 `TouchType.Down` 会重置，且 `candTryContinue` 内部有 `last < items.length - 1` 检查，不会误续页

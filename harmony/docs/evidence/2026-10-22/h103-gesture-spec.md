# H-103 · 手势规格（主人 2026-10-22 21:0x 口述）+ 与 H-096 合并成一次性改动

- 记录人：Qoder（只读记录与验收判据，**未改任何 `entry/src/**`**）
- 来源：主人 21:0x 口述「上滑键盘出键盘上的符号，下滑出大写字母，退格上滑或长按是清除，下滑是撤回」
- 目的：把 5 条手势要求**一次性**定死，**和 H-096-3／H-096-4／上滑顺序缺陷合并成一次改动、一次交付**——主人原话「一直在让他改键盘，闹心改一处错一处」，根因就是这几件事改的是同一块代码却分次改、每次只验一部分。

## 一、规格（5 条）

| 编号 | 手势 | 行为 | 现状 | 难度 |
|---|---|---|---|---|
| **S1** | 字母键**上滑** | 上屏该键**键面上已经印着的那个符号** | **已有**（就是键面左上角那个小字），但触发顺序有缺陷（H-096，未修） | 改触发方式 |
| **S2** | 字母键**下滑** | 上屏**大写字母**（该字母的大写） | **全新**，当前 `PanGesture` 只注册了 `PanDirection.Up` | 中 |
| **S3** | 退格键**长按** | **清除**整个输入（当前输入框内容全清） | 现在是**连删**（按住 500ms 后每 100ms 删 1 个） | 中 |
| **S4** | 退格键**上滑** | **清除**整个输入 | 全新 | 中 |
| **S5** | 退格键**下滑** | **撤回**上一次的输入 | 全新，**且引擎侧目前完全没有撤回能力**（全库检索无任何 undo 实现）。**API 已核实可行**（`InputClient.deleteForward` + `getForward` 读回校验），见 §四 与 `h103-undo-sdk-verification.md` | 中 |

**S1 的「键面上的符号」定义**：26 键布局 = 键面左上角那个 10 号灰字，来源 `ALT_CHARS`（`KeyboardIndex.ets:169-173`，q 行 `1..0`、a 行 `@ * + - = / # ( )`、z 行 `' : ? ! ~ \`）。九键布局 = 该键印着的那一个符号；**交付说明里必须写清九键用的是哪张表**，否则验收无从判。

**S2 的一条边界**：下滑出大写字母**不应改变 Shift 状态**（下滑出完大写，下一次单击仍是小写，除非 Shift 键本来是锁定的）。这条要在判据里写死，否则会出「一直是大写」的坑。

**S3/S4 的「清除」定义**：清掉**当前输入框里的全部内容**（含已上屏的文本），不是退格一个字符，也不是清候选。

**S5 的「撤回」定义**：把**上一次提交上屏的那段文本**从输入框里删掉（连字符一起删），并把引擎状态同步回退（preedit 与候选一起清）。**不是**「把上次输入的那几个拼音字母退成未上屏」——那是另一种行为，主人没这么说，先不做。撤回栈为空时**无反应**（不报错、不上屏任何东西）。

## 二、为什么必须一次改完（这是本单最重要的一段）

S1／S2／S3／S4／S5 加上 H-096-3（横屏预编辑宽度上限）、H-096-4（候选条数要扣预编辑宽度），**全部落在同一块代码上**：

| 代码位置 | 现状 | 本次要动什么 |
|---|---|---|
| `LetterKey()` `:1341-1382` | `onTouch`（Down/Up/Cancel）+ `PanGesture({direction: Up, distance: 20}).onActionEnd` | 上滑出符号 + **下滑出大写** + 顺序无关的触发 |
| 退格 ×3 处 `:1441`（qwerty 行内）／`:1638`（数字面板 `bs_num`）／`:1912`（符号面板 `bs_sym`） | 三处各写一遍 `onTouch`，共用 `startBackspaceRepeat()` / `stopBackspaceRepeat()` `:862-883` | 长按=清除、上滑=清除、下滑=撤回 —— **三处必须一致**，漏一处就会出现「行内退格能撤回、底栏退格不能」 |
| `startBackspaceRepeat()` `:862-871` | 500ms 后起 `setInterval` 每 100ms 删一次 | 改成：长按到阈值 ⇒ **一次性清除**（并停掉连删定时器） |
| 撤回栈 | **不存在** | 新增（见 §四） |

⇒ **一次改、一次构建、一次装机、一次交付**。分两次改必然出现「上滑好了下滑坏了」「长按清除好了退格撤回又坏了」。

## 三、触发方式的技术约束（避免再踩 H-096 那个坑）

H-096 已判定的缺陷：`onActionEnd` 与 `onTouch(Up)` 谁先谁后**无文档保证**，现在的写法（`onActionEnd` 出符号 + `onTouch(Up)` 判 `swipeAltDone`）存在**双上屏**风险。S1/S2 必须用**与顺序无关**的写法：

1. `PanGesture` 改成 `direction: PanDirection.All`（**不要在同一组件上注册两个 PanGesture**，同族手势会互相抢），在回调里用 `event.offsetY` 判方向：`offsetY < 0` = 上滑，`offsetY > 0` = 下滑。
2. 方向与「这次是不是滑动」的判定在 `onActionStart` / `onActionUpdate` 阶段就**置位**，不要等到 `onActionEnd`。
3. `onActionEnd` **只负责出字符**（上滑出符号 / 下滑出大写），**不碰** `swipeAltDone`。
4. `onTouch(Up)` 只在「**没有发生过滑动**」时才 `sendLetter(ch)`；发生了滑动就什么都不做。
5. `Cancel` 必须清掉滑动标记，不能让下一次单击被吞。

⇒ 这一套同时满足 S1 与 S2，也顺带把 H-096 那条「上滑双上屏」关掉。

## 四、撤回（S5）要新做的部分 —— 主人要知道这是本次唯一的新功能

全库检索 `undo` / `撤回` / `撤销`：**没有任何功能实现**（`KeyboardIndex.ets:83` 那个「撤销 D-009」是「撤回一条设计决定」，不是撤回功能）。所以 S5 不是改手势，是**从零做一个能力**。

### 4.1 API 已核实：可行（2026-10-22 21:2x 核实，详见 `h103-undo-sdk-verification.md`）

本应用**已经握着**能删文本的句柄：`inputMethodEngine.InputClient`（`KeyboardController.ets:134-140` 从 `inputStart` 拿到），SDK 原文（`@ohos.inputMethodEngine.d.ts`，`interface InputClient` `:1003`）：

| 方法 | 行 | SDK 文档原文 |
|---|---|---|
| `insertText(text)` | `:1169` | "Inserts text." |
| `deleteForward(length)` | `:1071` | "**Deletes the fixed-length text before the cursor.**" |
| `deleteBackward(length)` | `:1120` | "Deletes the fixed-length text **after** the cursor." |
| `getForward(length)` | `:1217` | "**Obtains the specific-length text before the cursor.**" |

> ⚠ **命名陷阱**：`forward` = 光标**前**，`backward` = 光标**后**，与英文直觉相反。本应用 `KeyboardController.ets:454-456` 已经写对了（退格用 `deleteForward`），**照抄，别"顺手修正"**。
> ⚠ 不要去 `@ohos.inputMethod` 的 `InputMethodController` 里找删除 API——那里没有（`:478` 只有 attach/detach/updateCursor/changeSelection 等）。

### 4.2 机制（定死，照做）

- **撤回栈放哪**：`KeyboardController`（`entry/src/main/ets/inputmethod/KeyboardController.ets`），因为撤回要知道「刚才上屏了哪几个字符」，那是输入法侧的职责，不该放在 UI 页里。栈深 ≥ 20。条目存 `{ text, len }`——**文本也要存**，下面校验要用。
- **入栈时机（只有一处）**：在 `insertText()`（`:442`）里入栈。全库上屏路径都经过它（`onKey()` `:314`、`chooseCandidate()` `:323`、`chooseCandidateAbs()` `:336`，S1 的符号路径 `onKey(alt)` 最终也落到这里）⇒ **在 `insertText()` 入栈就不会漏路径**。一次提交 = 一条。
- **撤回怎么做（带读回校验）**：
  1. 弹栈顶条目 `{ text, len }`；
  2. `getForward(len)` 读回光标前 len 个字符；
  3. **读回内容 ≠ 条目.text ⇒ 放弃、不删**，记一条日志（光标漂移 / 别人改过输入框 / 输入框被清过）；
  4. 一致 ⇒ `deleteForward(len)`；
  5. 引擎侧一起清：`engine.clear()`（preedit + 候选一起清），否则会出现「屏上字没了、候选还在」。
- **为什么加第 3 步**：光标可能被用户点了别处、或输入框被外部改过。此时若照着旧记录盲删，删掉的是**用户的别的字**——正是主人最烦的那类坑。有第 3 步，最坏情况是「没撤动」，而不是「撤错了」。
- **退格会改编辑器**：因此**除撤回以外的任何编辑器写操作（退格等），都把栈顶条目丢弃**（本单不做精细修剪）。
- **边界**：栈空 ⇒ 无反应（不报错、不上屏任何东西）；撤回之后如果用户又输入了新内容 ⇒ 撤回栈清空（不做重做）；连续撤回 ⇒ 逐条往回退；`inputStop` ⇒ 栈清空（换输入框就是换一段历史）。
- **异步注意**：`getForward`/`deleteForward` 是 Promise，手势回调里要用 `async` + 串行化，别让两次撤回并发。

### 4.3 S3/S4「清除全部」怎么做

需要先知道光标前总共有多少字符 ⇒ 用 `getForward` 阶梯探测：`64 → 256 → 1024 → 4096`，**返回长度 < 请求长度 ⇒ 那就是总量**，然后一次 `deleteForward(总量)`；同时 `engine.clear()` 清引擎侧。
现有 `clear()`（`:404`）**只清引擎编码，不清编辑框**，所以 S3/S4 需要新增一个「引擎 + 编辑框一起清」的口子，不能拿 `clear()` 顶替。

### 4.4 为什么长度账目是精确的

预编辑是**本应用自己画在候选栏里**的（`KeyboardIndex.ets:974` `Text(this.preedit)`），**没有写进编辑框**；写进编辑框的只有 `insertText` 的已提交文本。⇒ 光标前 N 个字符 **==** 最后上屏的 N 个字符，不用去猜 preedit 占了几格。

**验收判据（真机）**：打「你好」→ 退格下滑 ⇒ 输入框里「你好」整段消失且候选栏回到空；再点一次 ⇒ 无反应（栈空）；重新打字再撤回 ⇒ 只撤最近那段。

> 结论一句话：**第一部分的参考覆盖度分析可用、诚实；第二部分的「完成时间估算」现在不能采信**——它写在我 19:05 判退与主人 19:12/19:18 两次改方向之前，已经过期，且把最重的一块压成了半天。

## 一、可以采信的部分

**kanonIME 覆盖度表（第一部分）** 是全篇最有价值的一节，而且态度诚实：它没有把「我们抄了成熟实现」说成「项目快完了」，反而明确列出 **16 项里 13 项 kanonIME 根本没有**（中文引擎、三向反查、OpenCC 简繁、九宫格 T9、13 个 Lua 齿轮、词库闭包、弹性条数、手势翻页、中英/简繁合键、26 键与符号布局、预编辑语义），并给出「大约覆盖 2 成」的判断。这个比例和我们自己的账对得上，主人可以按它理解「复用开源省下的是哪一段」：**省下的是候选栏 UI 那 15% 里的大部分，不是项目整体的 80%。**

**风险清单里第 3 条（备案审核 7-20 个工作日）** 是真话，也是全篇唯一一个「不归我们管」的硬约束，值得单独看。**「M5 皮肤范围要主人确认」** 这条依赖也标得对。

## 二、不能采信的部分（逐条，都给了证据）

**1. 整份文档的「当前状态」已经过期，但它是主人现在会读的那一份。** 第三节写「信箱：所有消息 DONE，无 OPEN 任务」「阻塞点：无」。实际 `docs/MAILBOX.md` 现在有三条 **OPEN**：M-036（H-048 判 REWORK）、M-037（改单行）、M-038（预编辑挪到上一行）。他 19:10 落盘时，我 19:05 的判退他还没读到——**机制本身在跑（每 5 分钟轮询），但这份文件在主人眼里是「进度权威」，所以必须先失效标注再谈内容。**

**2. 它把「双行候选」当成已完成的核心成果。** 文中「M4 候选栏 v2 ✅ 编码完成：双行候选 + 反查行 + ▼ 展开网格」。双行已在 19:12 被主人作废（`DECISIONS.md` D-003），19:18 又定了新形态（D-004：预编辑独占上一行）。连带影响第一部分那条「候选栏 UI 覆盖度 ~80%」也要打折：真正抄来的四件事里，**双行那件已经不要了**；而唯一被真机判退的两条回归（F1 手指能把候选条拖走、F2 预编辑被 44vp 截断）**恰恰就是「抄 List 当翻页载体」抄出来的**（我们是引擎分页 + 手势分页）。

**3. 「自造词/自调频落盘 = 半天」是全篇最不可信的一条。** 这块是我负责的引擎侧，真实缺口是：三生那套 rime-lua 齿轮在 Windows 上依赖 `runLog.lua` / `sysInfo.lua` / `socket.lua` 和 `os.getenv('APPDATA')` + `installation.yaml`，**鸿蒙沙箱里一个都没有**——要先写鸿蒙实现或安全桩，再把用户词典/调频写到 filesDir，再 bump `DATA_VERSION` 让 17 MB 词库重编，再真机验「打完下次还在」「频率自己上调」。参照 M3 同一层的实际节奏（run6→run15 才把「候选恒 0 条」这个 bug 收口，见 `docs/evidence/2026-10-21/m3-close-run13-15-panel.md`），我给 **1~2 个工作日**，不是半天。

**4. 40% / 15% / 15% / 15% / 15% 这个工作量拆分没有方法。** 标题写「按工作量估算」，但既没有基准也没有推导，五个数字还正好凑成 100%。作为沟通可以理解，**不该被当成数据引用**——尤其「引擎侧 ~40%」这一格，而引擎侧（M2+M3）恰恰已经做完了，读的人会以为 40% 还没动。

**5. 时间单位没定义，最容易误读。** 「1-2 小时 / 半天 / 1-2 天」混着用，没说清是 **agent 工作时长** 还是 **自然日**。我们是两个定时轮询的 agent，不是 8 小时工时的人；而「核心功能可用 约 2-3 天」这种写法，主人很可能读成「2-3 天后就能装到手机上用」。

**6. 未定范围的东西被计进了总工期。** M5 皮肤/触感自己标了「依赖主人确认范围」，却又算进「核心功能可用」的 2-3 天里。范围没定的活不能计工期。

**7. 漏了几块硬缺口**（这才是我说「估算不能采信」的主因）：

| 漏项 | 现状 | 为什么影响工期判断 |
|---|---|---|
| **许可定案**（`ISSUES.md` **H-007，OPEN**） | 根 `LICENSE` 写 MIT，`fanxing_rime_har` 包声明 Apache-2.0，两处不一致 | 上架前必须有人拍板，这是法律问题不是代码问题；他列了「AGC 上架材料」却没列这条 |
| **正式开发者证书** | 我们全程用调试签名装机，**正式证书/账号资质从未核实过** | 「正式签名 + AGC 上架 半天」是凭空给的，前提都不存在 |
| **横屏可用宽度**（**H-040，OPEN，P3**） | 横屏键盘只有约 610vp 可用（屏宽 809vp），左右各约 316px 被系统图标占着 | 直接决定横屏一页能放几条候选，和刚定的弹性/单行设计绑在一起 |
| **九宫格英文/多击**（**H-028，OPEN，P2**） | 它两条 mock 局限其实都已真机 VERIFIED（① T9 数字进编码＝H-047；② `ascii_mode` 直出＝H-041/M-032），本轮我已关单。**但「九宫格要不要能按出英文单词」这条主人提过、我们没有对应需求单** | 属于**范围没定**而不是 bug；不定下来就会变成上架前才发现的活 |

| **升级与数据迁移** | `DATA_VERSION` 变更后老数据怎么处理，没有方案 | M4 一 bump 就会碰到，属于「做完才发现」的那类 |

**8. 顺带说一句我自己的账没记平。** `ISSUES.md` 里 H-008（上游 NAPI 桥只有 5 个接口）和 H-010（电脑版 schema/Lua/词库/OpenCC 未移植）其实早就在 M2/M3 做完了，状态还挂着 OPEN——**这会让任何按 ISSUES 算完成率的人都算低**。本轮我已把 H-008 / H-010 / H-028 三条按真机证据改成 VERIFIED。
